# Grace-period coding agent

A ready-made coding agent that runs shell commands in the background with the asynchronous shell implementations, turns finished background commands into automatic model turns, and pauses for a 2-second grace period before starting each shell command. During that pause the operator can abort the command, either with Ctrl-C or through a cancellation request from another part of the program, such as a supervising model. It also offers file reading, writing and a substring-replacement edit tool.

## Behaviour
- Invoked as `<agent> MODEL [TASK...] [--endpoint URL] [--session SESSION_ID]`. MODEL is a model id or a `run://` URI. The endpoint defaults to the standard default endpoint. `--session` resumes that session.
- With TASK words it runs the standard one-shot task mode on the words joined by spaces and exits, printing that mode's standard startup lines. Both modes get the `--session` value and the system prompt supplement below.
- Without TASK it runs its own REPL that behaves like the standard REPL (session resume with history replay, per-directory input history, `exit`/`quit`/`q` or end-of-input to leave, Ctrl-C interrupts the current turn, the messages snapshot is saved after every turn, and the resume command is printed on exit). The REPL banner is `secondguess-agent <MODEL>  (type 'exit' to quit)`.
- While waiting at the prompt, the REPL checks the completion queue every 250 ms. When one or more background commands have finished, and the prompt's edit buffer is empty, it abandons the pending prompt (printing a newline) and starts a new model turn for each completion, one at a time in completion order, with no user input. Completions that arrive during a turn are handled after that turn ends, before the prompt is shown again.
- Each automatic turn prints a dim line `[completion] <first line of the message>` and sends the model this message as the user turn:
  - First line: `Background command <id> finished after <duration with 1 decimal>s (returncode=<rc>).`
  - Then `stdout: <text>`, where text is the trailing-whitespace-stripped stdout if its capture file is at most 4096 bytes, and `(empty)` if that is empty. If the file is larger (or cannot be inlined), text is `(see <stdout path>)`, followed, when the file is readable and has at least one line, by a newline, `last 3 lines:`, a newline and the file's last 3 lines (fewer if it has fewer) joined by newlines.
  - Then `stderr: <text>` under the same rules, except that an empty inlined stderr yields no `(empty)` placeholder: the stderr part is included only when its text is non-blank.
- Uses an in-memory agent spec with `status: "default"` and structured tool calls, and offers five tools in this order: `exec_shell(command)`, `query_tool_exec(tool_exec_id)`, `read_file(path)`, `write_file(path, content)`, `str_replace_edit(path, old_str, new_str)`. `exec_shell` has the single required parameter `command`. All `str_replace_edit` parameters are required; it maps to the built-in substring-update implementation. `query_tool_exec`, `read_file` and `write_file` map to the built-in poll, read and write implementations.
- `exec_shell`:
  - Runs a 2-second grace period and checks for cancellation every 100 ms.
  - If no cancellation happened, it starts the command exactly like the asynchronous start implementation with no delay and returns that result.
  - If it was cancelled, the command is never spawned and the tool returns `{"cancelled": true, "command": "<command>", "message": "Command was cancelled during the 2.0s grace period."}`.
- Cancellation sources: Ctrl-C during the grace period, or a cancellation request from another thread. A request made before the grace period starts (for example, while the model is still generating the tool call) cancels the next command at once.
- The cancellation request is cleared at the end of every grace period, whether or not it caused a cancellation. A request therefore affects at most one command.
- The system prompt supplement is "You are a coding agent. Start shell commands with exec_shell — they run in the background. Use query_tool_exec to poll status. Pass `when` to exec_shell to delay a command by N minutes. When a background command finishes you will be notified automatically with its output." followed by a blank line and: "**Grace period**: every exec_shell call pauses 2.0s before actually starting the command. During this window the operator can Ctrl-C to abort. The command only begins after the grace period expires."
- `exec_shell` is described to the model, in this order, as: it starts a shell command asynchronously; it starts after a 2.0s grace period, during which the operator can cancel by pressing Ctrl-C (or a supervisor can request cancellation); it returns `tool_exec_id` and local file paths for stdin (FIFO), stdout and stderr; write to `stdin_localfile` to send input to the running process; if the command finishes within 100 ms and both outputs are under 4096 bytes, stdout/stderr are inlined immediately; use `query_tool_exec` to poll status; when a background command finishes the agent is notified automatically. The grace period is stated as behaviour, with no **IMPORTANT** warning or "does NOT start immediately" wording.
- `query_tool_exec` is described as polling a command started with `exec_shell` (its `tool_exec_id` is described as "The ID returned by exec_shell."). When the command has completed, the result includes the return code and inlines stdout/stderr if both are under 4096 bytes; otherwise it reports file sizes.

## Edge cases
- `exec_shell` no longer accepts a `when` delay; the system prompt supplement still mentions it verbatim, but there is no such parameter.
- A cancelled command has no execution id, no capture files and no completion event.
- A completion only interrupts the prompt while no complete input line is ready; a line already submitted is handled first, and the completion is handled right after that turn.
- A completion never interrupts partially typed input: while the prompt's edit buffer holds any text, finished completions stay pending and the prompt keeps waiting. They are handled right after the user submits that line and its turn ends (or, if the user clears the buffer, at the next 250 ms check).
- In a completion message, an empty stdout capture file reports `stdout: (empty)`, and an empty stderr file omits the stderr part. A too-large stderr always produces a stderr part, since its `(see <path>)` text is non-blank. The tail is read with undecodable bytes replaced; if the large file cannot be read, only `(see <path>)` is shown.
- In one-shot task mode, completion events are not turned into model turns.
