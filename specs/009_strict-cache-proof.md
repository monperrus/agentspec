# Strict cache proof

By default the agent checks prompt caching strictly. The first model call of a session must return explicit server-side cache accounting. If it does not, caching cannot work at all, and the turn is aborted while the cost is still only one call. Models that cannot prove cache reuse are treated as unsupported. After the first call, the tokens for the turn are already paid for, so a missing cache proof or a cache miss no longer aborts. The agent emits a temporary `cache_proof_missing` warning and continues. Callers and the CLI can opt out.

## Behaviour
- Strict mode is on by default for single tasks, the sync REPL and the async REPL. The CLI flag `--no-strict-cache-proof` disables it; programmatic callers can disable it per session.
- The session counts model calls that returned a usage block. The count spans the whole session, across turns; it is not reset per turn.
- Usage normalization, from the response `usage` object (`details` = `usage.prompt_tokens_details`):
  - Cached (cache-read) tokens are taken from the first of these fields that is present (non-null): `details.cached_tokens`, `usage.cache_read_input_tokens`, `usage.cache_read_tokens`, `details.cache_read_tokens`, `details.cache_read_input_tokens`; 0 if none is present.
  - Cache-write tokens are taken from the first present of: `usage.cache_creation_input_tokens`, `usage.cache_write_tokens`, `details.cache_write_tokens`, `details.cache_creation_input_tokens`; 0 if none is present.
  - The response carries cache proof when any of these nine fields is present, even with value 0, and even if only a cache-write field is present.
- These normalized values feed the per-response `usage` event/log record and the session totals (`cached`, `cache_write`) for every response, regardless of strict mode.
- Cache status: every session exposes a cache status to callers, `ok` or `missing`, so a UI can show a temporary status-bar warning. It starts as `ok`. In strict mode, any response with cache proof and either cached tokens > 0 or cache-write tokens > 0 sets it back to `ok`, on any call, before the other checks. Each `cache_proof_missing` warning sets it to `missing`.
- First counted call (session count 1), in strict mode: a response with no cache-proof field aborts the turn with the error `Strict cache mode requires explicit cache accounting from the server on the first LLM call, but this response exposed no cache-proof field.` A response that has cache proof passes, whatever its cached and cache-write counts, and no further check runs on it.
- In strict mode, for each response with a usage block, once the session count is 2 or more:
  - No cache-proof field → no abort. The status becomes `missing` and the agent emits `cache_proof_missing` with `cached_tokens` and `prompt_tokens`. It is displayed in yellow as `⚠ No cache accounting from the server after the first call; continuing without strict cache proof (tokens for this turn are already paid). Warning clears on the next observed cache hit.` and the response is processed normally.
  - Cached tokens ≤ 0 and cache-write tokens > 0 → a cache write counts as proof. The first call whose prefix crosses the provider's minimum cacheable size fills the cache, and the next call reads it. The agent emits a `cache_written` event with `cache_creation_tokens` (the cache-write count), displayed dim as `Prefix cache written this call (<cache_creation_tokens> tokens); the next call will read it back.`, with the count using comma thousands separators (e.g. `4,900`). The response is processed normally.
  - Cached tokens ≤ 0 and cache-write tokens ≤ 0 → unless the minimum-cacheable floor below applies, there is no abort. The status becomes `missing` and the agent emits `cache_proof_missing` with `cached_tokens` and `prompt_tokens`. It is displayed in yellow as `⚠ No cache hit after the first call (prompt <prompt_tokens> tokens); continuing without strict cache proof. Warning clears on the next observed cache hit.`, with the prompt count using comma thousands separators. The response is processed normally.
- Minimum cacheable prompt size: providers cache nothing below a provider-specific prompt size (e.g. ~4096 tokens for small Claude models, ~1024 for some GPT models). The floor comes from the agent spec field `min_cacheable_tokens` (integer, prompt tokens). It can be overridden per session by a programmatic argument (single task, REPLs, session creation) or by the CLI flag `--min-cacheable-tokens N`; an explicit argument or flag wins over the spec field. The default is 0 (no floor).
  - When the floor is nonzero and a response has cache proof, cached tokens ≤ 0, cache-write tokens ≤ 0, and a `usage.prompt_tokens` (0 if absent) strictly below the floor, the agent emits a `cache_below_minimum` event instead of the warning. The event carries `prompt_tokens` and `min_cacheable_tokens` and is displayed dim as `No cache hit, but prompt (<prompt_tokens> tokens) is below the provider's minimum cacheable prefix (<min_cacheable_tokens> tokens); not a caching failure.` The status is unchanged and the response is processed normally.
- In strict mode, a response with no usage block after at least one counted call does not abort. The status becomes `missing` and the agent emits `cache_proof_missing` with no token fields, displayed in yellow as `⚠ No usage metadata from the server after the first call; continuing without strict cache proof. Warning clears on the next observed cache hit.` Processing continues.
- Cold resume: before the post-first-call checks above, the agent measures the age of the session's most recent message that carries a timestamp (`ts`, ISO 8601 local time), as now minus that timestamp. If the age is strictly greater than 3600 seconds, the prefix cache is assumed to have expired:
  - A response with a usage block that lacks cache proof or reports cached tokens ≤ 0 emits a `cache_cold` event with `age` (whole seconds) instead of `cache_proof_missing`. It is displayed dim as `Prefix cache expired (last message <age>s old); this turn was not served from cache and will re-process the prompt.` and the response is processed normally.
  - A response with no usage block emits a `cache_cold` event with the dim display line `Prefix cache expired (last message <age>s old); usage metadata unavailable this turn.` and processing continues.
  - A response with cache proof and cached tokens > 0 passes silently; no `cache_cold` event is emitted.
  - A cold-resume notice leaves the cache status unchanged.
- The first-call abort emits an `error` event (displayed as `Error: <text>`) and appends an `error` log record. The turn then ends normally with the turn result (session id, the last non-empty assistant reply so far, cumulative usage, messages). It does not crash the REPL or the process.

## Edge cases
- A response without a usage block is not counted; if no call has been counted yet, it passes silently.
- On the first counted call, a zero cache hit with cache proof present passes; only a fully missing cache-proof field aborts.
- The first-call check runs before the cold-resume check: a first counted call with no cache proof aborts even if the last message is older than 3600 seconds, and the first counted call never emits `cache_cold`.
- The aborting first response is discarded: its usage is not added to totals or emitted, and its tool calls or reply are not processed.
- A response after a `cache_proof_missing` warning is not discarded: its usage is counted and emitted, and its tool calls or reply are processed.
- The warning is not one-shot: every qualifying call after the first emits its own `cache_proof_missing` event. The status stays `missing` until a later response reports a cache read or write.
- A present-but-zero field wins over later candidates: `details.cached_tokens: 0` with `usage.cache_read_input_tokens: 500` yields 0 cached tokens and counts as a miss.
- A response whose only cache field is a cache-write field has proof and 0 cached tokens. After the first call, it passes with a `cache_written` event if the write count is > 0, and is treated as a miss (floor relaxation or warning) if the write count is 0.
- A write-only response emits `cache_written` regardless of prompt size relative to the floor, and never `cache_below_minimum`.
- A response with both cached tokens > 0 and cache-write tokens > 0 passes silently; no `cache_written` event is emitted.
- With strict mode off, no cache check is made, missing usage blocks are tolerated, no `cache_cold` or `cache_proof_missing` event is emitted and the status is not updated.
- An age of exactly 3600 seconds or less is warm: misses get the `cache_proof_missing` warning.
- If no message has a timestamp, or the most recent timestamp cannot be parsed, the age is unknown and the checks apply unchanged.
- A prompt size equal to or above the floor with no cache hit gets the warning; a floor of 0 or null disables the relaxation.
- The floor does not excuse a missing cache-proof field or a missing usage block; those still get the warning after the first call and still abort on the first call.
- The cold-resume check runs before the floor check: if the session is cold, `cache_cold` is emitted instead of `cache_below_minimum`.
- A cache hit (cached tokens > 0) never emits `cache_below_minimum`, whatever the prompt size.
- The cold-resume relaxation is not limited to one event: every qualifying check while the age exceeds the threshold emits its own `cache_cold` event.
