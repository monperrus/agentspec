# Spec-driven coding agent

The agent is a coding agent that works with any OpenAI-compatible chat-completions endpoint. It is driven by a JSON agent spec that describes, for one model, which tools to offer, how that model delivers tool calls, and which built-in tool implementation handles each tool. The agent runs one task non-interactively or as an interactive REPL, dispatches the model's tool calls to local implementations, logs each session, and can resume a session later.

## Behaviour

### Agent spec (JSON)
- Recognised top-level fields: `model`, `endpoint`, `status`, `tool_specs` (OpenAI `tools` array; legacy name `inferred_tool_schema`), `tools` (implementation names paired with `tool_specs`), `behaviour.call_delivery_mode`, `behaviour.resume_rejects_stale_tool_call_ids`, `tool_dispatch` (legacy explicit dispatch), `aliases`, `options`, `provider`, `provider_api_support.streaming.supported`, `max_output_tokens`, `max_rpm`, `max_input_token_price_per_million`, `max_output_token_price_per_million`, `disabled`, `comment`, `display_name`, `auth`, `key_env`, `keyring_service`, `keyring_username`.
- `tool_dispatch` maps a model-facing tool name to `{"python_function": <built-in implementation name>, "param_map": {<model arg>: <implementation arg>}}`. Arguments not listed in `param_map` pass through unchanged.
- A spec is rejected before running if `disabled` is true (error message is `comment`, default "This agent spec is disabled.") or if the tool definitions (`tool_specs`, else `inferred_tool_schema`) are missing or empty ("No tool schema for '<model>' — probe likely failed.").

### Loading a spec
- An explicit spec path (CLI flag `--spec-path PATH`, or an equivalent optional argument for library callers) takes precedence over every other rule below. The file is read directly and its JSON returned as is, with no name-based lookup, no default spec and no `run://` handling of the spec (a `run://` endpoint still selects the subprocess backend). A leading `~` is expanded to the home directory; a relative path resolves against the current working directory. The dimmed notice `Using schema file <file name>` is printed.
- If the model argument ends in `.json`, it is read as a spec file path; a relative path is resolved against the installation's project root. The dimmed notice `Using schema file <file name>` is printed.
- Reading a spec file by explicit path or `.json` model argument fails with an invalid-spec error if the file does not exist (`Spec file not found: <path>`) or is not valid JSON (`Spec file <path> is not valid JSON: <parser message>`).
- Otherwise the spec is looked up first among the specs shipped in the installation's project root as `agent_spec_<safe>.json`, then `inferred_tool_schema_<safe>.json`, then `tool_schema_<safe>.json`, where `<safe>` is the model name with `/` and `:` replaced by `_`; the first existing file is used and the dimmed notice `Using cached probe at <file name>` is printed. If none exists, `agent_spec_<safe>.json` in the current working directory is used if present, with the dimmed notice `Using specification from <file name>`.
- The agent never probes a model itself. If no spec file exists and a non-empty endpoint is supplied, a default spec is generated in memory and used. It is never written to disk and no notice is printed. There is no option to skip existing spec files or force regeneration (the former `--reprobe` CLI flag no longer exists). The default spec has `model`, `endpoint` (the supplied one), `status: "default"`, `behaviour.call_delivery_mode: "structured_tool_calls"`, and the four default tools below as `tool_specs` and `tools`.
- If no spec file exists and the endpoint is empty, it fails with an invalid-spec error: "No agent spec found for '<model>'. Run `llmprobe <model>` (with --endpoint <endpoint> if needed) to probe the model and generate a spec file." No spec file is written.
- `run://<binary path>` as endpoint or model selects a local subprocess backend. Its spec file is `agent_spec_<safe>.json` in the directory containing the binary (after resolving the binary path to an absolute, symlink-free path), not in the installation directory; it is only ever read from there, never written. If that file exists, it is used and the agent prints the dimmed notice `Using specification from <file name>`. Otherwise a default spec is generated in memory and used without being saved. The default spec has `status: "default"`, structured tool calls, and four tools: `read_file(path, offset?: integer, limit?: integer)`, `write_file(path, content)`, `str_replace(path, old_str, new_str, replace_all?: boolean)`, `exec_shell(command)`. The `str_replace` description is `Edit an existing file by replacing a specific substring. By default replaces only the first occurrence; pass replace_all=true to replace every occurrence.` and `replace_all` is described as `Replace every occurrence of old_str instead of only the first (default false).`. Only `path` is required for `read_file`; `offset` is described exactly as `Line number to start reading from (1-indexed).` and `limit` as the maximum number of lines to read. The built-in read implementation selects the whole file when neither is given and the file has at most 100 lines (see the read-result bullet under Turn loop for longer files); otherwise it selects at most `limit` lines (all remaining lines when `limit` is absent), starting at line `offset` (line 1 when absent), with original line endings preserved. An `offset` of 0 or any negative value is treated as 1; negative offsets do not count from the end of the file. An `offset` past the last line yields an empty result. The default dispatch for `str_replace` has `param_map` `{"old_str": "old", "new_str": "new"}`, so the model's `old_str`/`new_str` arguments reach the string-replacement implementation; the other three have an empty `param_map`. The default spec stores the tools as `tool_specs` and `tools`, and the dispatch is derived from them.
- Default endpoint: `https://openrouter.ai/api/v1`.

### Aliases and options
- `aliases` maps an alias name to a canonical tool name. At session start the canonical dispatch entry is copied under the alias, and in structured mode a copy of the canonical tool schema is added under the alias name. An alias that already has its own `tool_dispatch` entry keeps it. An alias whose canonical tool has no dispatch entry is skipped with a warning.
- The built-in shell tool was formerly named `execute_shell_command` and is now `exec_shell`. The retired name is a built-in alias of `exec_shell`, always applied at session start before the spec's own `aliases` (a spec entry for the same alias name overrides it). Specs, cached spec and tool-schema files, and restored sessions that still use `execute_shell_command` therefore keep dispatching to the shell implementation unchanged.
- The built-in retired-name alias is dispatch-only: it adds a dispatch entry but never adds a tool schema, so a default session offers the model `exec_shell` only, never both `exec_shell` and `execute_shell_command`. A model or restored session that emits `execute_shell_command` still runs the shell tool. A spec that itself declares a tool named `execute_shell_command` offers exactly that tool, once. Aliases declared in the spec's `aliases` (including one reusing the retired name) are still offered to the model as described above.
- A call to an unknown tool returns to the model, as the tool result, `<error>. Available tools: <list>. Call one of the available tools instead.`, where `<list>` is the sorted, quoted (`'name'`), comma-separated dispatch names, or `(none)`. The list omits `execute_shell_command` whenever `exec_shell` also has a dispatch entry, so a typo never surfaces the retired name next to `exec_shell`. When `execute_shell_command` is present and `exec_shell` is absent (e.g. a pre-rename spec whose only shell tool is the retired name), it stays listed.
- The built-in retired-name alias applies only when the session has a dispatch entry for `exec_shell`. A custom toolset without one (e.g. a single shell tool renamed `shell`) gets no `execute_shell_command` dispatch entry and emits no warning at session start; the "canonical tool has no dispatch entry" warning is reserved for aliases declared in the spec.
- `options` is an array of strings. `exclude-prompt_cache_key` suppresses the `prompt_cache_key` request field; the `user` field is still sent.

### Session
- A session id is 12 random hex characters, or the id of the session being resumed.
- Call delivery mode is `structured_tool_calls` (default) or inline. In structured mode the system prompt is "You are a helpful coding agent. Use the provided tools to complete the task. When finished, reply in plain text." In inline mode the system prompt is `Tool calls are made by responding with a single JSON object on its own line:`, then one example per tool (`{"name": ..., "arguments": {...}}` with `<arg>` placeholders), one per line, then a blank line and `After each call you will receive the result. When the task is done, respond with a plain-text summary.` The prompt describes the expected response only positively (no "ONLY", "no prose", "no markdown fence" or "no JSON" interdictions).
- At session start, the system prompt is extended in this order, each part separated from the previous by a blank line: an optional caller-supplied supplement, then the contents of the user's global instructions file `~/.claude/CLAUDE.md` (in the home directory) if it exists, then the contents of `AGENTS.md` in the current working directory if it exists. A missing file is silently skipped.
- In non-interactive mode, tools that map to the ask-the-user implementation are removed from the offered tools; if the model still calls one, the result is `ERROR: user interaction is disabled (--non-interactive)`.
- Every request uses temperature 0 and sends a cache key as `user` and (unless excluded) `prompt_cache_key`. The cache key defaults to the session id; a caller may supply a stable one without resuming the conversation. `max_tokens` is set from `max_output_tokens` when configured. In structured mode `tools` and `tool_choice: "auto"` are sent.
- Against an OpenRouter endpoint, requests also send `usage: {"include": true}` and `provider` from the spec. If the spec has no `provider`, the session pins to the provider that served the first response (`{"order": [<provider>], "allow_fallbacks": false}`) and emits a `provider_pinned` event.
- When the spec says streaming is supported, content and reasoning deltas are emitted as they arrive.

### Turn loop
- A turn appends the user task and then repeatedly calls the model:
  - Structured mode with tool calls: the assistant message with its tool calls is recorded, each call is dispatched in order (unparseable arguments become `{}`), and each result is added as a `tool` message.
  - Inline mode: every JSON object in the reply that has `name` (or `function_name`) and a dict `arguments` (or `parameters`) is a call. Several calls in one reply are dispatched in order, and their results go back as one user message: `Tool results:\n` followed by `[<name>] <result>` blocks separated by blank lines.
  - Otherwise the reply is the final answer and the turn ends.
- Messages sent to the model keep user/assistant alternation. If the last message in the conversation already has role `user` when a turn starts (for example after an aborted or failed turn), the task is merged into it rather than appended as a new message. The merged content is the old content, a blank line (`\n\n`), then the task. If the old content is empty, the merged content is just the task. The merged message's `ts` becomes the current time. The `user` log record still holds only the new task text.
- The turn result has the session id, the final reply (the last non-empty assistant content, or none), cumulative usage (`prompt`, `completion`, `total`, `cached`, `cache_write`) and the message list.
- Token budget: each turn has a budget of 3,000,000 effective tokens. Each response adds `max(0, prompt_tokens - cached_tokens) + completion_tokens` to the count; cached prompt tokens do not consume budget. The cumulative usage `total` still records the raw API total. When the count exceeds the budget, a `token_limit` event fires with the message `[stopped after exceeding <limit> effective tokens (used <used> effective)]`; if the session has cached tokens, ` (<raw total> raw API total, <cached> cached)` is inserted after `effective` inside the parentheses. Numbers use thousands separators. Interactively, the user is asked whether to double the budget (`y`/`yes` continues). Otherwise the turn stops with no final reply. A turn stopped by the budget (the user declined, or the session is non-interactive) still returns a normal turn result (session id, final reply as defined above, cumulative usage, messages), never an empty value.
- Built-in file tools (read, write, string replace, update file, list directory, search files given a plain directory path) expand a leading `~` or `~user` in the path argument to the home directory before accessing the filesystem. Result messages still quote the path as the model gave it.
- The built-in string-replacement tool takes `path`, the old text, the new text and an optional boolean `replace_all` (default false), which passes through dispatch unchanged. The old text must occur verbatim in the file, whatever `replace_all` is; otherwise the file is left unchanged and the result starts with `ERROR: old string not found`. Let N be the number of occurrences before the edit and D the number replaced: D = 1 by default (only the first occurrence, scanning from the start), D = N with `replace_all` true.
  - The result is `OK: replaced <D> of <N> occurrence(s) (<L> line(s), <C> UTF-8 character(s)) in <path>`, where L is D × the old text's line count (newlines + 1, or 0 for empty text) and C is D × the old text's length in characters. Example: `OK: replaced 1 of 1 occurrence(s) (1 line(s), 4 UTF-8 character(s)) in f.txt`.
  - When D < N, the result continues with `; <N − D> remaining — pass replace_all=True to replace them`. When all occurrences were replaced, nothing is appended.
- The built-in read tool wraps the selected text in an XML-like envelope whose tag name is a checksum: `<CHECKSUM>content</CHECKSUM>`, where `CHECKSUM` is the first 8 lowercase hex digits of the SHA-256 of the selected text's UTF-8 bytes, and the content is inserted verbatim (no escaping, no added newlines). This lets the model tell file versions apart across turns, and lets an auditor check a logged read against the content it covered.
  - When `offset` and/or `limit` apply, the opening tag carries them as attributes, in this order and with double quotes: `<CHECKSUM offset="<offset>" limit="<limit>">`. An attribute appears only when that value applies, and holds the value as given (e.g. `offset="0"` even though 0 is read as line 1).
  - If neither `offset` nor `limit` is given and the file has more than 100 lines, only the first 100 lines are returned, as if `offset` were 1 and `limit` were 100. The tag then reads `<CHECKSUM offset="1" limit="100">`. No other truncation notice is added; the model can ask for more with `offset`/`limit`.
  - The metadata `result` holds the same envelope text. On failure (e.g. missing file) the result is the `read_file` internal-error text described below, with no envelope.
- The built-in shell-command tool runs the command string with `/bin/bash`, not `/bin/sh`, so bash syntax (e.g. `[[ ... ]]`, brace expansion, `source`, process substitution) works.
- The built-in shell-command tool returns compact JSON with no whitespace between tokens (separators `,` and `:`), with keys in the order shown:
  - When the command finishes: `{"stdout":<string>,"stderr":<string>,"returncode":<integer>}`, whatever the exit code. Empty output gives empty strings; there is no `(no output)` placeholder and no `[exit N]` suffix. The metadata has `stdout`, `stderr`, `returncode`, `streamed: true` and `result` (the returned JSON text).
  - On any failure to run the command other than a timeout: `{"error":"<message>"}`. The metadata has `error` and `result`, both the returned JSON text.
- The built-in shell-command tool gives a command at most T seconds, where T = TTL − 20, clamped to a minimum of 1. The TTL is the time-to-live budget for one synchronous tool execution: the value given by a library caller when creating the session, else the agent spec's optional integer field `tool_ttl_seconds`, else 600 (so T defaults to 580). The 20-second margin leaves room to return partial output when a command times out. A TTL that is not a number or is ≤ 0 falls back to 600; a fractional TTL is truncated to an integer. Examples: TTL 300 → 280 s; TTL 21 → 1 s; TTL 10 → 1 s.
- On timeout the shell-command tool kills the command's whole process group, then waits up to 2 seconds for each of stdout and stderr to be read to the end. It returns `{"error":"command timed out after <T> s","stdout":<partial stdout>,"stderr":<partial stderr>,"hint":<hint>}`:
  - The hint is `The command did not finish within <T> seconds. For long-running commands, use 'nohup <command> &' to run in the background.`. If the current agent spec's `tool_dispatch` maps any tool to the implementation `t_execute_async`, the hint continues with ` Or use t_execute_async to start the command asynchronously.`. Otherwise the asynchronous implementation is not mentioned.
  - The metadata has `error` and `result` (both the returned JSON text), plus `stdout`, `stderr` and `hint` (each as a separate field).
- The built-in search tool (arguments: a `path`, default `.`, and a `pattern`) runs a line-numbered grep over the path, with a 30-second limit. It returns compact JSON with no whitespace between tokens (separators `,` and `:`):
  - On success: `{"matches":[{"file":<string>,"line":<integer>,"text":<string>},...]}`, one entry per grep output line of the form `file:line:text`, in grep's output order. The line is split on the first two `:` only, so `text` may itself contain `:`. With no matches the result is `{"matches":[]}`.
  - On timeout, the search's whole process group is killed and the result is `{"error":"search timed out after 30 s"}`. On any other failure it is `{"error":"<message>"}`.
  - The metadata has `result` (the returned JSON text), plus `matches` (the match list) on success or `error` (the message) on failure.
- A call to a tool with no `tool_dispatch` entry (e.g. `exec_command` when only `exec_shell` is exposed) is not fatal: the process keeps running, the turn continues, and the tool result returned to the model is `ERROR: no dispatch entry for tool '<tool name>'. Available tools: <names>. Call one of the available tools instead.`. `<names>` are the session's dispatch entry names, sorted, each single-quoted, joined by `, `, or `(none)` when there are none. It is journaled, emitted and logged like an ordinary tool result. An unknown implementation name or bad arguments also return an `ERROR: ...` string to the model.
- Tool failures carry enough detail to locate the fault from the result alone. A "frame list" is the innermost (up to) three stack frames of the error, innermost last, each written `<source file base name>:<line> in <function name>` and joined by `, `.
  - Malformed tool invocations are the model's fault, so their errors are written to let the model correct the call on its next iteration.
  - An argument mismatch when invoking the implementation (a missing required argument, an unexpected or wrongly named argument) is not fatal and returns `ERROR: invalid arguments for tool '<tool name>': <error message>. Expected signature: <implementation name>(<parameter list>). You supplied: [<names>]. Correct the argument names/values and call the tool again.`. `<names>` are the argument names the model sent (before parameter mapping), sorted, each single-quoted, joined by `, `. When the implementation's parameter list cannot be determined, `(...)` is shown instead. The metadata `result` holds the same text. Example: calling `str_replace` with `path` and `old_string` when it expects `old_str`/`new_str` yields a result starting `ERROR: invalid arguments for tool 'str_replace'`, showing the implementation's parameters and listing `['old_string', 'path']`.
  - Any other error escaping a tool implementation during dispatch (an internal tool failure) is not fatal and returns `ERROR: tool '<tool name>' raised <error type name>: <error message> (<implementation name>(<call arguments>); <frame list>)`. The metadata `result` holds the same text.
  - An implementation that returns a non-text result (e.g. a boolean) has it converted to its text form (`True` → `True`); the metadata `result` is replaced by that text.
- Built-in file and search tools convert non-string values of their string arguments (`path`, the old text, the new text, `patch`, `content`, `command`, `pattern`) to their text form before use, so a model sending e.g. `old_str: true` gets an ordinary result (here `ERROR: old string not found ...`) rather than an internal error, and writing `content: false` writes the text `False`.
- When a built-in read, write, string-replace, list-directory, glob, search-files or find-files tool fails (e.g. missing file), the result is `ERROR: <tool> internal error: <error type name>: <error message> (<frame list>)`, where `<tool>` is respectively `read_file`, `write_file`, `str_replace`, `list_dir`, `glob`, `t_search_files`, `t_find_files`. Refusals the tool detects itself (e.g. old string not found) keep their own messages.
- If a model call fails (network, HTTP or API error), the turn does not crash. A context-window rejection is handled differently: the agent compacts and retries (see the context compaction spec). An `error` event fires with text `API error: <message>`, an `error` log record is written with field `error` holding the same text, and the turn ends at once with the result so far (no final reply unless one was already produced).
- In the REPL and in the interactive CLI loop, any other unexpected error during a turn fires an `error` event with the error message and writes an `error` log record. The loop then continues to the next prompt, and the conversation snapshot is still saved.
- On start, both the sync and the async REPL print a bold banner followed by `  (type 'exit' to quit)` and a blank line. The banner text is the spec's `display_name` when that field is present, and otherwise the agent's program name, a space, and the model name.
- On REPL start, before any resumed history is replayed, the REPL prints `Tools:    ` (label plus four spaces) followed by the model-facing tool names joined by `, `, in definition order. The names come from `inferred_tool_schema` when it is non-empty, and otherwise from `tool_specs`. A tool definition without a `function.name` is shown as `?`. With no tool definitions the line is `Tools:    (none)`.
- Ctrl-C during a turn kills the running tool subprocess (its whole process group) and aborts the turn back to the prompt. At the prompt, Ctrl-C is ignored. A caller can also cancel a turn from another thread; the turn stops at the next model-call boundary (before a model call, or right after one returns).

### Events
- The agent reports progress as typed events, each carrying a pre-formatted display string: `tool_call`, `tool_result`, `usage`, `token_limit`, `final_answer`, `session_usage`, `session_resumed`, `session_restored`, `provider_pinned`, `content_delta`, `reasoning_delta`, `content_stream_end`, `reasoning_stream_end`, `error` (displayed as `Error: <text>`). A caller can supply its own event handler. By default, the display string is printed (`token_limit` to stderr, and streaming deltas without a newline).
- A displayed tool result shows at most its first 40 lines, each indented by two spaces. When the result has more than 40 lines, one more line `  … (<n − 40> more lines)` follows, where `<n>` is the total line count. A result with exactly 40 lines or fewer has no such line. A displayed tool call is shown as `▶ <name>(<args>)`, where `<args>` lists each argument as `<key>=<quoted value>` separated by `, `. When `<args>` is longer than 400 characters, only its first 400 characters are shown, followed by `…`; at exactly 400 characters or fewer it is shown in full with no `…`.

### Logging and resume
- Each session appends JSON Lines records to `~/.local/share/agent_probe/<safe model>/<YYYY-MM-DD>/<HHMMSS>_<session id>.jsonl`. Record types: `session_start`, `session_resumed`, `session_restored`, `user`, `usage`, `tool_call`, `tool_result`, `fatal_error`, `error`, `provider_pinned`, `assistant`, `session_end`. Every record has `ts` (ISO seconds) and `cwd`. A `tool_result` record has the tool `name`, the name of the implementation that handled it, and `result`, the full result text returned to the model.
- After a task, the conversation is saved to `~/.local/share/agent_probe/<safe model>/<session id>_messages.json`, but only if it has at least one non-system message. Messages that lack `ts` get one. The model directory is created if missing.
- The snapshot file is a JSON object (UTF-8, 2-space indent) with two keys: `metadata`, an object with `endpoint` (the endpoint base URL, or `""` if unknown), `model` (the model name as given, not the safe name) and `session_id`; and `messages`, the array of messages.
- The snapshot `metadata` also records tool provenance, so a snapshot traces back to the exact tool definitions in force when it was written:
  - `tools`: the model-facing tool names, in definition order. A definition's name is taken from `function.name`, or from a top-level `name` when there is no `function` object, and is `?` when neither exists. When the session was given no tools (absent or empty), the default tool set was used and its names are listed explicitly: `["read_file", "write_file", "str_replace", "exec_shell"]`.
  - `default_tools`: `true` when no tools were given, and also when the given tool names equal the default list exactly (same names, same order); otherwise `false`.
  - A third key, whose name contains the product name, holds the git commit id (full `HEAD` hash) of the source checkout the running agent was loaded from. It is `"unknown"` when the agent is not running from a git checkout (e.g. an installed package) or the lookup fails for any reason. The lookup never fails the save.
- The snapshot `metadata` also has `auth`: the authentication *configuration* the session was started with, so a resume can re-create the client (together with `endpoint`, `model` and `tools`) without the wrapper that launched the original session. It records exactly one key source, following the key resolution order:
  - When both `keyring_service` and `keyring_username` are given (non-empty), `auth` holds those two fields and `key_env` is omitted, even if it was given.
  - Otherwise `auth` holds `key_env` if given, and neither keyring field (a lone `keyring_service` or `keyring_username` is not recorded).
  - The configuration field `auth` (the auth scheme, e.g. `"opencode-github-copilot"`) is independent of the key source and is included whenever given, alongside either source.
  - Only fields with a non-null value are included, copied as is. It is `{}` when none apply. It never contains the resolved API key or any other secret value, only how to obtain it.
- Resuming by session id loads that snapshot. If none exists for the current model, the most recently modified snapshot with that id under another model is used, with a notice. If no snapshot is found anywhere, a warning is shown and the session starts fresh.
- A resumed session (`--session <id>` on the CLI, or a session id given to a library one-shot or REPL run) always continues on the endpoint it was *created* on, not on the endpoint that `--endpoint`, the CLI default or a wrapper resolved. The endpoint and key source are rebound before the spec is validated, before prices are checked and before the client is created:
  - The recorded metadata is the snapshot `metadata` for the session id in the current model's directory only. A snapshot with that id under another model is never consulted: resuming with another model is a deliberate provider switch (see the cross-model session port spec), and a foreign endpoint must not leak into the binding. A legacy array snapshot, or an unreadable one, contributes nothing. When the current model has neither a snapshot nor logs for the id, nothing is rebound.
  - The session logs for that id in the current model's log directory override the recorded `endpoint`: the endpoint of the earliest `session_start` record wins. Log files are ordered by `<YYYY-MM-DD>/<HHMMSS>_<id>.jsonl`, and only each file's first record is looked at. The logs are append-only, so this also corrects a snapshot that an earlier resume against the wrong provider overwrote.
  - When the recorded endpoint is non-empty and differs from the resolved one, the recorded endpoint replaces it.
  - When the recorded `auth` is a non-empty object, the key-source fields `auth`, `keyring_service`, `keyring_username` and `key_env` are taken from it exactly. A field present in the recorded `auth` is set to its recorded value. A field absent from it is removed from the configuration, never merged, so key resolution cannot fall through to a key for another provider.
  - When anything changed, a one-line notice is printed: `Resuming session <id> on its original endpoint '<endpoint>' (<changes>)`, where the changes are joined with `; ` and each reads `endpoint '<old>' → '<new>'` (`∅` for an empty old endpoint), `<field> → '<value>'` or `<field> dropped`.
  - The caller's configuration is never modified; the rebinding applies only to the resumed run.
  - The rebinding also happens when a session is initialised directly with a resumed session id (as a library caller or the TUI does, building its own client), not only through the CLI, one-shot or REPL entry points. The initialised session's `endpoint` is the recorded one, and every snapshot it saves records that endpoint in `metadata.endpoint`, so a resume never overwrites the session's origin endpoint.
- A snapshot loaded by exact id (for the current model or from another model) is normalised before it is resumed. By default, consecutive user messages are merged into one, and nothing else changes: assistant tool calls and `tool` messages are kept as structured messages, so the model can still tell a tool that really ran from text it wrote itself.
- The spec field `behaviour.resume_rejects_stale_tool_call_ids` (boolean, default `false`) is for providers that reject tool call ids minted in an earlier API session. When it is `true`, the resumed history is also flattened to plain text, in order:
  1. Consecutive user messages are merged into one.
  2. An assistant message with tool calls is removed; its own text content is dropped. Each call is paired with the later `tool` message whose `tool_call_id` equals the call's `id`.
  3. A `tool` message becomes an assistant message with content `prior tool use: <name>(<args>) -> <outcome>`, using its paired call's name and arguments. It keeps its own `ts`, or the call message's `ts` if it has none. A `tool` message with no paired call uses name `?` and empty args.
  4. A call without an `id` becomes, in its place, an assistant message `prior tool use: <name>(<args>) -> unknown`. A call with an `id` but no matching `tool` message is appended at the end of the history in that same form, in call order, with the call message's `ts`.
  5. Consecutive assistant messages are merged into one.

  `<args>` is the raw arguments string (non-string arguments are serialized to JSON text, non-ASCII kept as is), with every run of whitespace collapsed to one space and leading/trailing whitespace removed; if longer than 200 characters it is cut to 200 and `…` is appended. `<outcome>` is `error` when the trimmed result text, lowercased, starts with `error` or `traceback` or contains `exception`, and `ok` otherwise (including an empty result). The result payload itself is never copied into the flattened history, and no bracketed `[Tool call: …]` / `[Tool result: …]` text is produced. The flattened history has no tool calls and no `tool` messages.
- Merging joins the contents with a blank line (`\n\n`); if the earlier content is empty, the later content is used alone. The merged message takes the later message's `ts`.
- After merging (and flattening, when enabled), every resumed history gets a tool-call pairing repair, so that strict providers (which reject with HTTP 400 an assistant tool call not followed by a `tool` message for its id, or a `tool` message with no preceding matching call) accept it. The history is walked in order:
  - An assistant message opens a tool-call block holding the ids of its tool calls (compared as strings; calls without an `id` are not tracked).
  - A `tool` message is kept only when its `tool_call_id` is still unanswered in the current block, and that id then counts as answered. Any other `tool` message (no matching call, an id already answered, or after the block was closed) is dropped.
  - The next assistant, user or system message closes the block. Before it, one placeholder `tool` message is inserted for each unanswered id, in call order, with that `tool_call_id` and the closing message's `ts`. When the closer is an assistant message, the placeholder content is `[tool result lost: the session was interrupted before this tool call completed; verify state before retrying]`. When it is a user or system message, the content is `[tool result lost: <name> was interrupted before completing; verify state before retrying]`, where `<name>` is the call's custom-tool name, else its function name, else `?`.
  - Ids still unanswered at the end of the history get placeholders of the second form, appended at the end, with `ts` null.
- The repair creates no other change: a history whose calls and `tool` messages are already paired is left as is. A flattened history has no tool calls or `tool` messages, so the repair leaves it unchanged. No tool is re-executed.
- A session can also be resumed by a short id of the form `<prefix>-<8 chars>` (any id whose last `-`-separated part is 8 characters long). When no snapshot file matches the id exactly, the short id matches a snapshot whose real session id hashes, as the first 8 lowercase hex digits of SHA-256 over its UTF-8 bytes, to that last part. The prefix is ignored. The current model's snapshots are searched first. Other models' snapshots are searched only when no other model has a snapshot with that exact id.
- The agent shows the user a resume command, i.e. the shell command that continues the current session. `<program>` is the running executable exactly as it was invoked (the path or name the process was started with), in both the one-shot and REPL modes.
  - When `<program>` is the agent's own CLI, the resume command is `<program> <model> --session <session id>`, because that CLI takes the model as a positional argument. `<program>` counts as the agent's own CLI when its final path component is the agent's main command name or `agent-probe` (the REPL command), or when it resolves to the agent's own entry-point script.
  - Any other executable is treated as a wrapper that pins its model, and the resume command is `<program> --session <session id>`, with no model argument (e.g. `/home/u/bin/agent-glm-5.2.py --session 4e55afe7c1ce`).
  - A library caller can force the model argument to be included or omitted, overriding the executable-based decision.
- An environment variable that overrides the resume command lets a wrapper script present itself: when it is set and non-empty, the resume command is `<value> --session <session id>`, with no model argument, because the wrapper is assumed to choose the model itself.

### Credentials and client
- `run://` specs use the subprocess backend. Each request runs the binary once, with a 300-second timeout. If the binary writes to stderr, the agent prints `  [subprocess stderr] <stderr>` with the full, untruncated stderr text. A non-zero exit code is an error whose message is `Binary '<path>' exited <code>: <stderr>`, again with the full stderr text. Otherwise stdout is parsed as a JSON chat-completion response.
- `auth: "opencode-github-copilot"` reads `github-copilot.access` from `~/.local/share/opencode/auth.json` and sends it in the `X-API-Key` header.
- Every HTTP chat-completion request carries the authentication header, `Content-Type: application/json`, and an `X-Title` header whose value is a fixed, lowercase label naming the agent. Gateways and routers use `X-Title` to attribute traffic to a client, so per-client token accounting can tell this agent's requests apart from other clients' instead of counting them as unknown.
- A library caller building an HTTP client can supply extra request headers. They are applied last, after the default headers, so an extra header with the same name replaces the default (e.g. `X-Title: custom-label` replaces the agent's label). No extra headers means only the defaults are sent.
- HTTP clients enforce a client-side rate limit per endpoint base URL. All clients for the same base URL share one limit, and the first client created for that URL sets it. The limit is the spec's `max_rpm` (requests per minute) when present, and 40 otherwise. `run://` subprocess backends are not rate-limited.
- Each HTTP request attempt has a 300-second timeout. When an attempt times out while waiting to read the response, the agent retries up to 5 times after the initial attempt, waiting 1, 2, 4, 8, then 16 minutes (60 × 2^(n−1) seconds before retry n). Before each wait it prints `  [read-timeout] request timed out — retry <n>/5 in <minutes>m …`. If the sixth attempt also times out, the read-timeout failure propagates to the caller unchanged. Other connection failures (e.g. a connect timeout or refused connection) are not retried.
- When an HTTP request gets a transient server-error response (status 500, 502, 503, 504 or 529), the agent retries up to 5 times after the initial attempt. Before retry n it waits the delay stated by the response headers (same headers and parsing as for 429 below; the body is never consulted) when that delay is positive, and otherwise 5 × 2^(n−1) seconds (5, 10, 20, 40, then 80 s). Before each wait it prints `  [HTTP <status>] transient server error — retry <n>/5 in <seconds, 0 decimals>s …`. If the sixth attempt also gets one of these statuses, the agent prints `  [HTTP <status>] <first 2000 characters of the response body>` and the request fails with an HTTP error for that status, which aborts the turn as an API error. No `rate_limit_wait` event fires for these waits.
- Other non-success statuses (e.g. 400, 401, 404) are not retried: the first response fails the request at once.
- Before each HTTP request attempt (including retries after HTTP 429, a transient server error or a read timeout), if the limit's number of requests has already been made within the last 60 seconds, the agent prints `  [rate-limit] <N> RPM limit reached — waiting <seconds, 1 decimal>s …` and waits until the oldest of those requests is 60 seconds old. Waiting clients are served one at a time.
- When an HTTP request gets a 429 response, the agent retries only if the response states a retry delay. The delay comes from the first of these headers that is present and well-formed: `retry-after-ms` (milliseconds), then `Retry-After` (delta-seconds, or an RFC 7231 HTTP-date meaning the time until that date; a date without a time zone is taken as UTC), then `x-ratelimit-reset-requests` (seconds). Negative delays are clamped to 0. The agent prints `  [rate-limited] waiting <seconds, 1 decimal>s (resuming at <HH:MM:SS> <zone>) …`, where the resume time is the current local wall-clock time plus the delay, in 24-hour format, followed by the local time zone abbreviation (e.g. `CEST`). Just before printing, it emits a `rate_limit_wait` event (see the event subscription spec). It then waits that long and resends the request. This repeats for as long as 429 responses keep stating a delay.
- Z.ai / BigModel endpoints (base URL host containing `z.ai` or `bigmodel.cn`, case-insensitive) state the delay only in the response body, e.g. `{"error":{"code":"1308","message":"Usage limit reached for 5 hour. Your limit will reset at 2026-08-16 05:42:29"}}` (the Anthropic-style variant wraps the same sentence in brackets). For these hosts only, when no header gives a usable delay, the agent searches the body text for `reset at YYYY-MM-DD HH:MM:SS` (case-insensitive), reads the timestamp as Beijing time (UTC+8, no DST), and uses the time until it as the delay, clamped to 0 if already past. A delay over 6 hours is rejected as a misread. For all other hosts the body of a 429 is never read.
- A 429 response with no usable retry delay is a rate-limit error; the request is not retried. The error message says the server returned HTTP 429 without a retry delay (no `Retry-After`, `retry-after-ms` or `x-ratelimit-reset-requests` header and no reset time in the response body), so the agent stops instead of retrying blindly. A library caller can tell this error apart from other failures, and it carries the status code and the response headers.
- On a Z.ai / BigModel host, this rate-limit error also carries the provider's business error code and message, read from the body's `error.code` and `error.message` (each converted to text; absent if missing or null). They are absent when the body is not JSON or has no `error` object, and always absent for other hosts.
- If the rate-limit error happens during a turn's model call, the turn ends without crashing. An `error` event fires whose text is the error message (the console shows it prefixed with `Rate limited: `), an `error` log record is written with `error` holding the message and `error_kind` set to `rate_limit`, and the turn returns the result so far.
- If it happens during CLI startup, the process exits with the message `Rate limited: <message>`.
- A library caller running a one-shot task, or starting the sync or async REPL, can inject its own chat-completions client (for example a sandboxed, wrapped or instrumented HTTP or subprocess client) instead of the one the agent would build from the spec. When a client is injected, the agent builds none and sends every model request of that session through the injected client. The spec is still validated first and still supplies the tools, prompts, model name and session state. When no client is injected, the agent builds the client from the spec as usual. The same injected client can be reused across several sessions in one process.
- For non-`run://` endpoints without an injected client, the API key is resolved from exactly one source. An agent spec should configure one key source only: `key_env` or `keyring_service`+`keyring_username`, not both; when both are present the keyring source wins.
  - Keyring source (both `keyring_service` and `keyring_username` non-empty): the system keyring entry for that service/username, then the environment variable named by `keyring_username` uppercased with `-` replaced by `_`. If neither yields a non-empty key, an authentication error is raised naming the keyring service/username and that environment variable; when the keyring support is not installed, the message says so and suggests installing it or setting the variable.
  - `key_env` source: the named environment variable. If it is unset or empty, an authentication error is raised naming the variable.
  - A configured source that yields no key never falls through to `API_KEY` or `OPENROUTER_API_KEY`.
  - No source configured, endpoint host (default endpoint if none given) contains `openrouter.ai`: `OPENROUTER_API_KEY` is obtained through the OpenRouter key-management flow (balance check and key rotation). `API_KEY` is never consulted, even when set.
  - No source configured, any other endpoint (for example z.ai, Mistral or `localhost`): the generic `API_KEY` is read as a plain key (environment, then keyring), then `OPENROUTER_API_KEY` the same way (kept for backward compatibility with wrappers that exported it as a generic channel). The first non-empty one wins, so `API_KEY` takes precedence when both are set. No balance check or rotation runs. If neither yields a key, an authentication error is raised naming the endpoint and saying to set `API_KEY`, or `key_env` or `keyring_service`+`keyring_username` in the spec.
  - An endpoint that cannot be parsed as a URL is treated as non-OpenRouter.

### Pricing check
- Before running, the current per-million-token input and output prices are fetched: from the OpenRouter models API for OpenRouter endpoints, or from the Azure Retail Prices API for Azure endpoints (the Azure data is cached on disk for 7 days, and global prices are preferred over data-zone prices). The prices are displayed.
- If a price exceeds `max_input_token_price_per_million` or `max_output_token_price_per_million`, the run is refused with a pricing-limit error that names the direction (input or output), the current price and the limit.
- `run://` and other endpoints show "no price check". If the price fetch fails, a warning is shown and the run proceeds.

## Edge cases
- A structured tool call whose arguments are not valid JSON (including an empty arguments string), or are valid JSON but not an object (for example an array, string, number or `null`), is never dispatched. Its result is `ERROR: malformed tool call arguments for '<tool name>': <parse error message>. Received: '<first 200 characters of the raw arguments>'. Re-emit the tool call with valid JSON object arguments.`; for a non-object the parse error message is `arguments must be a JSON object`. The agent journals a `tool_start` (with `args` `{}`) and a `tool_end` with that result and `outcome` `error`, emits a `tool_result` event with the text, writes a `tool_error` log record (`name` the model-facing tool name, `result`, `ts`), and appends a `tool` message with the call's `tool_call_id` and the text as content. The turn then continues with the remaining calls and the next model call, so the model can re-emit the call (e.g. arguments `{"path": ` for `read_file` produce one such `tool` message and the turn still finishes with the model's next reply).
- When a resumed session's history is replayed for display, a call whose arguments are not valid JSON or not an object is displayed with empty arguments.
- Inline JSON objects that fail to parse are skipped; scanning resumes at the next `{`.
- A resumed session keeps the resumed id as its session id; if no snapshot is found, it starts fresh under that id.
- A fresh session with only the system message leaves no snapshot.
- Resume rebinding is a no-op, with no notice, when neither a snapshot nor a log knows the session, when the snapshot is a legacy array without metadata and no log exists, or when the recorded endpoint and key source already match. With logs but no snapshot, only the endpoint is rebound. Example: a session created on z.ai and resumed through the OpenRouter default continues on z.ai with its recorded keyring source, and an inherited `key_env` is dropped (instead of failing with a spurious 402 Payment Required from OpenRouter).
- Two tasks in a row with no assistant reply between them (for example, the first turn hit an API error) produce one user message, not two consecutive user messages. A conversation that ends in an assistant or tool message gets a new user message as usual.
- Loading a snapshot (exact id, short id, or from another model) accepts both formats: an object with a `messages` key yields that array, and a legacy snapshot that is a plain JSON array of messages is used as is. A snapshot whose messages are not an array counts as not found.
- An explicit spec path wins even when a spec named after the model exists in the installation root or the current working directory, and even when the endpoint is empty or a `run://` URI; its `endpoint` field is returned unchanged. An empty spec path counts as not given.
- A default spec is never cached: every load that falls back to it regenerates it in memory and leaves the filesystem untouched.
- An exact snapshot id match always takes precedence over short-id resolution. An id with no `-`, or whose last part is not 8 characters long, is never treated as a short id.
- A `display_name` that is present is used verbatim in the banner, even when it is empty; the model name is not appended.
- The startup tools line prefers `inferred_tool_schema` over `tool_specs`, the reverse of the order used when validating the spec.
- If the resume-command override variable is set but empty, the default resume command is used.
- The resume-command override variable, when set and non-empty, wins even when a library caller forces the model argument to be included.
- An empty program name is never treated as the agent's own CLI, so it gets no model argument.
- A 429 whose delay headers are all missing, empty or unparseable (e.g. `retry-after-ms: not-a-number`) raises the rate-limit error; there is no fallback delay. A malformed header does not block the next one: an unparseable `retry-after-ms` falls through to `Retry-After`, and so on. A `Retry-After` of `0` or an HTTP-date in the past retries at once.
- On a Z.ai / BigModel host, a usable delay header takes precedence over the body. A 429 body that is empty, has no `reset at` timestamp (e.g. an insufficient-balance error), has an unparseable timestamp, or resets more than 6 hours from now raises the rate-limit error. The same body text from any other host is ignored and raises the rate-limit error.
- The read-timeout retry budget is counted per request, across all its attempts: 429 retries in between neither reset nor consume it. It is fresh for every new request.
- The transient server-error retry budget is likewise per request and independent of the read-timeout budget and of 429 retries. Example: five 502 responses followed by a 200 succeed after waits of 5, 10, 20, 40 and 80 s; a 503 with `Retry-After: 30` followed by a 200 succeeds after a single 30 s wait. A stated delay of 0 falls back to the exponential delay rather than retrying at once.
- A shell command that exits non-zero is not an error result: its JSON has `stdout`, `stderr` and the non-zero `returncode`, and no `error` key.
- A file of exactly 100 lines, read with no `offset` or `limit`, is returned whole with a bare `<CHECKSUM>` tag. A read that selects nothing (empty file, or `offset` past the end) still gets an envelope, with the checksum of the empty string (`e3b0c442`).
- An injected client does not bypass spec validation: a disabled spec or one without tool definitions is still rejected before any request is made.
- Search output lines with fewer than two `:` separators, or whose second field is not an integer line number, are silently left out of `matches`.
