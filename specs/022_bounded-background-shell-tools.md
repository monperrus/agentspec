# Bounded background shell tools

A ready-made trio of model-facing tools runs shell commands in the background like the asynchronous shell execution implementations, but with a bounded run time: `nohup` starts a command, `nohup_query` polls one, and `nohup_wait` blocks on one execution until it finishes or an optional budget expires, instead of busy-polling, reporting CPU/I/O activity when it is still running. A caller adds all three tools, with their model-facing definitions and their dispatch, to any agent spec in one idempotent step.

## Behaviour
- The implementation registry has implementations named `t_nohup` and `t_nohup_wait`, next to `t_execute_async` and `t_query_exec`.
- `t_nohup` takes `command` (string, required), `timeout` (integer minutes, optional, default 10) and `wait_before_s` (number of seconds, optional, default 0). It starts the shell command `timeout <timeout × 60> <command>` through the asynchronous start implementation with the same `wait_before_s`, and returns exactly what that start returns (same JSON fields, inline output rule, FIFO stdin, completion event, and the scheduled result for a delayed start). E.g. `sleep 30` with the default becomes `timeout 600 sleep 30`; with `timeout` 3 it becomes `timeout 180 sleep 30`; with `wait_before_s` 300 it is still `timeout 600 sleep 30`, started 300 s later.
- The `timeout` bound counts from the moment the command starts: a `wait_before_s` delay is not counted against it; the full budget is available once the command runs.
- The `timeout` value is truncated to an integer before converting to seconds.
- `t_nohup_wait` takes `tool_exec_id` (string, required, first), `howmuch` (number, optional) and `unit` (string, optional, default `s`). Units: `s` = 1 s, `m` = 60 s, `h` = 3600 s, `d` = 86400 s. When `howmuch` is given, `howmuch × unit` seconds is the wait budget, capped at 3600 s per call; without `howmuch` there is no budget and it waits until the execution completes.
  - It waits for that one execution, checking at least every 100 ms, and returns as soon as it has completed (immediately if it already had). Meanwhile it consumes completion events: the target's own event ends the wait; events of other executions are collected without ending it.
  - On completion it returns `{"tool_exec_id": <id>, "completed": true, "returncode", "duration_time" (seconds since start, 3 decimals), "stdout_localfile", "stderr_localfile", "command" (the full started command, including the `timeout` prefix), "stdout_last_lines", "stderr_last_lines"}` (last-lines excerpts as used by polling; empty string for empty output), plus inline `stdout`/`stderr` under the same 4096-byte rule as polling. There is no `waited_seconds`.
  - When the budget expires first it returns `{"tool_exec_id": <id>, "completed": false, "waited_seconds": <real time elapsed in this call, 3 decimals>, "activity": {...}, "hint": "not completed yet; call nohup_wait again for this tool_exec_id with a fresh howmuch budget."}`. The execution keeps running.
  - `activity` describes the still-running process and its direct children: `cpu_seconds` (user + system CPU time, 3 decimals), `cpu_percent` (100 × `cpu_seconds` / seconds since start, 1 decimal), `io_bytes` (object with integer `rchar`, `wchar`, `read_bytes`, `write_bytes`: bytes read/written since the previous not-completed report for this execution, or since its start) and `note` `bytes read/written since the last nohup_wait report of this execution`. Flat CPU and zero I/O deltas indicate an idle or hung process. Where the platform does not expose these counters, values are 0.
  - If the budget expires while a delayed execution has not started yet, the not-completed result also has `"scheduled": true` and `starts_in_seconds` (remaining delay, 3 decimals, never below 0), and its `activity` reports zero CPU and I/O with `note` `command not started yet (wait_before_s delay)`. Without a budget, the wait covers the delay and then the run.
  - If other executions completed during the wait, the result also has `also_completed`: a list of `{tool_exec_id, returncode, duration_time, stdout_localfile, stderr_localfile}`. Consumed events are not reported again by a later `nohup_wait`; `nohup_query` still reports each execution's final state.
  - E.g. after `nohup` of `echo hi && sleep 1`, `nohup_wait(<id>, 5, "s")` returns after ~1 s with `completed` true, `returncode` 0, `stdout_last_lines` `hi`. After `nohup` of `sleep 30`, `nohup_wait(<id>, 1, "s")` returns after ~1 s with `completed` false and `waited_seconds` ≈ 1. A wait can also end early because the user typed something (see the interruptible nohup_wait spec).
- Tool `nohup` (dispatched to `t_nohup`):
  - Parameters: `command` (string, "Shell command to run.", required), `timeout` (integer, "Maximum minutes the command may run before being killed (default <N>). Counts from the moment the command starts, not from wait_before_s.", optional) and `wait_before_s` (number, "Seconds to wait before starting the command (default 0). Cap 3600s. The tool returns immediately with tool_exec_id and file paths; poll/wait on that id as usual.", optional).
  - Description: `Start a shell command asynchronously, like nohup(1). Returns tool_exec_id, the process id (pid), and local file paths for stdin (FIFO), stdout, and stderr. Write to stdin_localfile to send input to the running process. Execution is bounded: the command is killed after `timeout` minutes (default <N>). If the command finishes within 100 ms and both outputs are under 4096 bytes, stdout/stderr are inlined immediately. To run a command in N seconds from now, pass wait_before_s=N: the command starts N seconds later and its full `timeout` budget is available when it starts.`
  - Neither model-facing text tells the model what not to do with the delay (no mention of a `sleep N &&` prefix); the delay is described only positively.
- Tool `nohup_query` (dispatched to `t_query_exec`):
  - Parameter: `tool_exec_id` (string, "The tool_exec_id returned by nohup.", required).
  - Description: `Poll a command started with nohup. When completed, includes returncode and inlines stdout/stderr if both are under 4096 bytes; otherwise reports file sizes. While a command is still running, nohup_wait(tool_exec_id, howmuch, unit) is the efficient way to let it finish.`
- Consecutive-poll redirect: the process remembers the `tool_exec_id` of the last successful poll (one shared tracker, across sessions). A poll of that same id while its execution is still running is redirected: it returns, without polling, the JSON object `{"error": "nohup_query was just called for this tool_exec_id and it is still running", "hint": "nohup_wait(tool_exec_id, howmuch, unit) returns as soon as it finishes.", "tool_exec_id": "<id>"}`. A redirected poll does not change the tracker, so further repeats stay redirected.
  - The redirect lifts when another id is polled (e.g. poll A, poll B, poll A → the third poll succeeds), when any new execution is started (the tracker is cleared), or when the execution has completed (a poll of a completed execution always returns its final state).
- Tool `nohup_wait` (dispatched to `t_nohup_wait`):
  - Parameters: `tool_exec_id` (string, "The tool_exec_id returned by nohup.", required), `howmuch` (integer, "Optional wait budget in the given unit. When reached with the execution still running, the tool returns instead of blocking further.", optional) and `unit` (string, enum `["d", "h", "m", "s"]`, "Time unit for howmuch: s=seconds, m=minutes, h=hours, d=days. Waits above 3600s are rejected; split long waits into several calls.", optional). Only `tool_exec_id` is required.
  - Description: `Wait for a background command started with nohup to finish. Takes a mandatory tool_exec_id and an optional howmuch × unit wait budget. Returns as soon as that execution completes, reporting returncode, output file paths and the last lines of stdout/stderr. If the budget (if given) expires first, reports completed: false together with the CPU and I/O activity of the still-running process, so you can tell progress from a hang; then call nohup_wait again for the same tool_exec_id. Without howmuch, waits indefinitely until it completes. The wait is cut short if the user types something meanwhile (interrupted_by: user_input): end your turn and answer them, the completion will be reported to you automatically.`
- `<N>` in the descriptions is the default bound the caller chose when enabling the tools (10 unless overridden). The definitions are listed in the order `nohup`, `nohup_query`, `nohup_wait`.
- Enabling the tools on an agent spec modifies the spec in place and returns it:
  - The tool definition list is the spec's existing `tool_specs`, else its `inferred_tool_schema`, else empty. The three definitions are appended, and the resulting list is stored under both `tool_specs` and `inferred_tool_schema`.
  - If the spec has a `tools` list (implementation names parallel to the definitions), `t_nohup`, `t_query_exec` and `t_nohup_wait` are appended to it, in that order, so it stays aligned with the definitions.
  - Otherwise `tool_dispatch` is created if missing, and gets `nohup` → `t_nohup`, `nohup_query` → `t_query_exec` and `nohup_wait` → `t_nohup_wait`, each with an empty parameter map.

## Edge cases
- The tool is named `nohup_wait` (formerly `wait_for`); no `wait_for` tool definition, dispatch entry or `t_wait_for` implementation name is provided any more, and all model-facing texts (descriptions, hints, notes) refer to `nohup_wait`.
- Enabling is idempotent: if a tool named `nohup` is already among the definitions, the spec is left unchanged (no duplicate definitions, `tools` or dispatch entries).
- The default bound passed when enabling only changes the descriptions shown to the model; a call that omits `timeout` is still bounded at 10 minutes.
- When the bound expires, the command is terminated by `timeout`, so the completion event and poll report its exit status (124 for a normal timeout kill).
- `nohup_wait` validation happens before any waiting; each failure returns the JSON object `{"error": ...}` immediately. The budget is validated first (only when `howmuch` is given; `unit` alone is ignored), then the id: an unknown id → `unknown tool_exec_id: <id>`. Budget errors:
  - unknown unit → `unknown unit '<unit>', expected one of d/h/m/s`;
  - a wait ≤ 0 (`howmuch` zero or negative) → `howmuch must be a positive number`;
  - a wait above 3600 s → `wait of <seconds>s exceeds the 3600s cap` (e.g. 3601 s, `2 h`, `1 d`). Exactly 3600 s (`1 h`) is accepted.
- `t_nohup` validates `wait_before_s` itself before starting anything, with the same errors as the asynchronous start (`wait_before_s must be >= 0`, `wait_before_s exceeds the 3600s cap`).
- Model-facing texts of these tools (descriptions, hints, redirect messages) are phrased positively: they state facts and the recommended tool, never words like "denied", "instead of busy-polling" or "do not poll".
- Polling a delayed execution that has not started yet is never redirected and does not update the consecutive-poll tracker; the tracker is cleared when the delayed command actually starts.
- Fractional `howmuch` values are accepted by the implementation (e.g. 0.01 s).
- The low-level `t_execute_async` / `t_query_exec` implementations remain available under their names and unbounded; the consecutive-poll redirect belongs to `t_query_exec` itself, so it also applies to any tool dispatched to it, and starting an execution through `t_execute_async` also clears the tracker.
- An unknown `tool_exec_id` keeps its original `unknown tool_exec_id` error and is not subject to the redirect.
